# Проверка контракта и сценариев

В проекте используются два вида проверок.

**Schemathesis** строит запросы по OpenAPI и проверяет ответы: предусмотрен ли HTTP-код, соответствует ли тело схеме, присутствуют ли обязательные заголовки. Источник контракта — `contracts/openapi.yaml`.

**pytest** проверяет последовательности действий. Например: создать заявку, повторить запрос с тем же ключом, убедиться, что ID не изменился и доступная сумма не уменьшилась дважды. Такие правила нельзя проверить только по форме одного ответа.

## Команды

В активированном окружении из корня проекта:

```bash
# Проверки готового окружения
python -m pytest -m 'not assignment'

# Корректность OpenAPI
python -m openapi_spec_validator contracts/openapi.yaml

# Контрактные проверки
python -m pytest tests/test_contract.py

# Все проверки задания
python -m pytest -m assignment

# Весь набор
python -m pytest
```

Для подробного вывода добавьте `-vv`. Для остановки на первой ошибке — `-x`.

Неполный шаблон контракта нужно заполнить до запуска контрактных проверок. В исходном сервисе есть ошибки; падение сценарных тестов до исправлений ожидаемо.

## Порядок разбора ошибки

1. Найдите требование, которое проверяет тест.
2. Сведите запрос к минимальному примеру и повторите его на чистой базе.
3. Сравните HTTP-код, заголовки и тело ответа с контрактом.
4. Проверьте состояние данных после запроса, если операция их меняет.
5. Запишите причину в отчёт и добавьте проверку, которая обнаруживает проблему до исправления.

Если ошибка в спецификации, исправьте её по требованиям. Если контракт верен, меняйте сервис. Удаление ограничения ради успешного теста скрывает проблему.

## Что покрыть сценарными тестами

- Создание и получение заявки, получение заказа, пустая и непустая выдача списка.
- Отсутствующие ресурсы и ошибки валидации пути, тела, заголовка и параметров запроса.
- Повтор создания с тем же ключом и тем же телом, а также конфликт при изменении тела.
- Ограничения валюты, статуса заказа и доступной суммы возврата.
- Два одновременных запроса к одному остатку.
- Подтверждение, отклонение и запрет переходов из конечных статусов.
- Освобождение суммы после отклонения.
- Фильтрацию, сортировку, пагинацию и `total` до применения страницы.

Используйте отдельный временный файл SQLite для каждого теста. Даты и порядок ответов проверяйте по требованиям; UUID создаваемых заявок не нужно фиксировать заранее.
